# 物品摆放工具 —— 设计说明

> 面向工程视角的设计记录：为什么做、怎么分层、关键数据结构与算法、和运行时系统的耦合取舍、已知限制。
>
> 使用说明见 [`物品摆放工具.md`](物品摆放工具.md) 与 [`内部碰撞体编辑器.md`](内部碰撞体编辑器.md)。

---

## 1. 背景：要解决什么问题

生存沙盒里"世界掉落物"是玩法内容的载体：桌上的一把刀、货架上的罐头、冰箱里的药品。手工一处处摆既慢又难对齐，于是需要一个**批量摆放**能力。真正难的不是"把预制体实例化"，而是三件事：

1. **表面从哪来** —— Unity 的 `Physics.Raycast` **只认 `Collider`**，采样区域也来自 `Collider.bounds`。美术资产的内腔（冰箱隔板、货架层板）通常**没有碰撞体**，对射线是"透明"的。
2. **摆哪儿不出错** —— 物品轴心普遍在模型中间，直接对齐轴心会半埋；物品自带的 `BoxCollider` 可能比模型更低，进 Play 会被物理去穿透顶出去；间距不够会互相叠。
3. **进 Play 会不会跑** —— `ItemPhysicsUtil.PrepareWorldDrop()` 的第一步是 `transform.rotation = Random.rotationUniform`（给"掉落物"用的随机姿态）。编辑器里精心摆好的姿态一进 Play 就被打乱并开始下落，从架子上滚出去。

工具链就是围绕这三件事设计的。

## 2. 设计目标与约束

| 目标 | 落地方式 |
|---|---|
| **零运行时开销** | 全部逻辑放在 Editor 程序集（`DownBreak.System.Interaction.Editor`），只在编辑期生成预制体实例 |
| **尽量不侵入美术资产** | 生成的碰撞体一律挂在 `InteriorCollider_*` / `AnchorSupportCollider` 子节点，可整体移除；不改原网格、不改原组件 |
| **数据源统一** | 物品只从 Luban 物品表取（`world_prefab_path`），短名解析走打包配置的 `assetAliasList`，与运行时掉落完全同源 |
| **可复现** | 随机种子可填；干跑统计与生成使用同一套采样逻辑 |
| **失败可解释** | 采样失败按原因分类计数（不是静默 `return false`），窗口直接告诉使用者"为什么摆不上" |
| **不破坏既有架构** | 生成物仍是普通世界掉落物（`ItemInteract` + `itemTableID`），拾取走既有 `IUIBagInteract` 链路 |

规模参考：工具窗口 1343 行、采样器 1295 行、配置与候选池 393 行、内部碰撞体编辑器 501 行、锚点组件 190 行。

## 3. 三层摆放策略（能力的递进）

不是"一个算法通吃"，而是按场景可控性分三层，能自动就自动，自动不可靠时给可控的手工通道：

| 层 | 方式 | 适用 | 依赖 |
|---|---|---|---|
| L1 | **表面采样**：包围盒内缩撒点 → 向下射线 → 只取法线朝上的面 | 桌面、地面、箱顶等开放表面 | 目标自身有实体碰撞体 |
| L2 | **内部采样**：内腔随机高度向下射线；或显式"内部表面"清单 + 多命中里挑最近的内部面（可越过箱体外壳） | 有内腔几何的容器 | 内腔面有碰撞体 |
| L3 | **锚点**：场景里手工摆 `ItemPlacementAnchor`（原点即承托面，局部 `+Y` 为法线） | 几何不可用、或要求精确对位 | 无（可自带承托碰撞体） |

L3 是关键取舍：与其让工具"猜"内腔，不如提供一个**美术/策划可拖拽的显式契约**，同时把"承托"这件事也交给锚点（可选生成薄 `BoxCollider`，顶面与锚点面重合）。

## 4. 关键数据结构与算法

### 4.1 配置与持久化

`SurfacePlacerSettings`（`[Serializable]`）分三段：采样（层掩码、内缩、间距、倾角、内部参数、净空开关）、物品来源（ID 列表 / 类型·稀有度过滤）、放置（件数、挂载方式、离面抬升、对齐方式、随机种子、运行时行为）。窗口用 `EditorPrefs + JsonUtility` 持久化，**场景引用（内部表面列表）留在窗口的 `[SerializeField]` 字段里**——避免把 `UnityEngine.Object` 引用塞进 JSON。

### 4.2 候选物品池

`SurfacePlacerItemPool` 把"选哪些物品"从"摆在哪"里解耦：

- **ID 列表模式**：每条 `{itemId, weight, stackCount}`，按权重抽取，支持同一物品重复出现；
- **类型随机模式**：遍历物品表，按 `EItemType` / `EItemRarity` 过滤；
- 两种模式都**强制要求 `world_prefab_path` 非空**，因此家具/储物箱（只有 `place_prefab_path`）会被自动跳过并计入统计——这类错误在配置阶段就暴露，而不是生成时逐件 `Debug.LogWarning`。

### 4.3 采样与诊断

`WorldItemSurfaceSampler` 是核心，采样一次命中要过六道检查：

```
包围盒内缩(margin + 物品半径)
  → 随机撒点
  → 向下 Raycast(层掩码 = 用户掩码 ∪ 目标自身层；掩码为 0 时退回 DefaultRaycastLayers)
  → 命中体是否属于目标碰撞体集合
  → 法线倾角是否 ≤ 阈值
  → 与已用点间距是否 ≥ max(最小间距, 物品自身宽度)
  → 净空盒测(按物品尺寸收缩 0.85，忽略触发器/目标自身/锚点承托体)
```

每一道失败都记进 `SurfaceSampleReport` 的对应计数（射线未命中 / 命中非目标 / 法线不够朝上 / 内部无遮挡 / 太近 / 附近已有掉落物 / 净空不足），窗口把它渲染成人话。这是本工具里最实用的设计点：**采样失败率高的场景，问题几乎都在这几个分类里**（层掩码、目标未激活、不是场景实例、内腔没碰撞体、贴墙）。

层掩码的一个细节：`表面层` 会**自动并入目标自身碰撞体所在层**。否则 `Interactable` 层的冰箱/箱子会被默认掩码（排除 UI/玩家/Interactable）整个挡掉，表现为"一个点位都采不到"。

### 4.4 落位对齐

`AlignBottomToSurface()` 取**渲染器包围盒 ∪ 碰撞体包围盒**在承托面法线方向上的最低点（8 个角点投影取最小），把它对齐到「承托面 + 离面抬升」：

- 用渲染器：保证视觉不半埋；
- 一起用碰撞体：保证物理不会因为碰撞体比模型低而被去穿透顶出去（这正是"进 Play 被顶飞"的一个来源）；
- 取两者更低者 = 只可能略微"浮"一点，绝不会陷进去。

另留 `落位对齐 = 轴心对齐锚点`，用于"我要 Transform 数值和锚点完全一致"的场景（代价是轴心在中间的模型会半埋）。

### 4.5 短名解析

物品表的 `world_prefab_path` 是短名，编辑期解析链路：完整 `Assets/` 路径直取 → `BuildBundleConfigura` 的 `assetAliasList` → 兜底按同名唯一预制体（**重名直接放弃**，避免摆错资源）。与运行时的 Addressables 别名体系同源。

### 4.6 锚点

`ItemPlacementAnchor`（放在运行时程序集，场景可序列化、工具与运行时都能用）：

- 数据：散布方式（单点/范围）、范围尺寸、件数覆盖、离面抬升、随机偏航、是否可作承托面；
- `SamplePoint()`：单点返回原点（可选小抖动用于多件），范围模式在 `areaSize` 内均匀撒点；
- `ResolveRotation()`：`FromToRotation(up, 锚点法线) * AngleAxis(yaw, up)`，先绕自身 up 转朝向再整体贴合法线，斜面上也站得住；
- Gizmo：承托台画在平面下方、平面细框、向上箭头、名称/范围/件数标签 —— **让"承托面在哪"在场景视图里无歧义**（早期版本把平面画成盒子中间面，直接导致"锚点和物品位置对不上"的误判）。

### 4.7 生成与撤销

`PrefabUtility.InstantiatePrefab` 保持预制体关联；每次生成用 `Undo.SetCurrentGroupName` + `CollapseUndoOperations` 包成**一次撤销**；「清空生成物」按分组节点名（或生成物名前缀）定位并 `Undo.DestroyObjectImmediate`。

## 5. 与运行时系统的耦合

### 5.1 交互优先级（摆放暴露出的既有缺陷）

"架子上摆的小刀拾取不到，只能聚焦到架子"这类问题，根因在 `InteractionDetector`：

- 球投射缓冲只有 **1**，直接取 `castHitBuffer[0]` —— 谁先返回聚焦谁，架子挡在前面时小刀永远轮不到（`NonAlloc` 还不保证顺序）；
- `ResolveInteractable` 把"不可交互碰撞体"缓存成 `null`，之后命中缓存直接 `return cached` → **一次检测被整体否决**；
- 缓存里的组件被销毁（物品被拾取）后，接口引用仍非 null，会拿到已销毁对象。

改造：缓冲扩到 24，遍历全部命中，按 **优先级 → 命中距离** 取最优；优先级由 `IInteractPriorityProvider`（可扩展）与 `InteractPriorityUtil` 统一表达：

```
可拾取物品 100  >  按压式交互 60  >  容器/工作台/可拆物 20  >  普通 0
```

不可交互的命中只跳过自己（不再否决整次）；缓存命中时校验 Unity 对象存活，销毁则清除重查。

### 5.2 运行时行为（为什么默认不随机翻姿态）

`ItemPhysicsUtil.PrepareWorldDrop()` 是给"扔到地上"用的（随机姿态 + 自由下落 + 落地转 Trigger）。编辑器摆场物走新加的 `PrepareStaticPlaced()`：**刚体运动学 + 关重力 + 碰撞体保持实体**，于是

- 不进世界物理 → 不随机翻姿态、不下落、不会被别的碰撞体挤压顶飞；
- 碰撞体仍是实体 → 依旧能被交互射线拾取，也仍是"物品"。

对应工具的 `保持编辑位置 / 正常世界掉落物` 两态。这是一个明确的取舍：**摆场物默认是"场景陈设"，不是"掉落物"**。

### 5.3 依赖方向

```
ItemPlacementAnchor            → DownBreak.System（运行时程序集，场景可序列化）
WorldItemSurfaceSampler 等工具  → DownBreak.System.Interaction.Editor（仅编辑器）
```

工具引用 System 与打包配置（`MieMieFrameWork.Editor`）读取别名，**不反向引用 UI / Gameplay**，符合工程的依赖方向约定。

## 6. 为什么是「锚点 + 承托 + 冻结」三件套

| 方案 | 优点 | 代价 |
|---|---|---|
| 直接给内腔补碰撞体 | 物理、射线全都"自然"了 | 侵入美术资产；内腔碰撞体是实体，会影响玩家碰撞与其它系统射线；大网格 `MeshCollider` 有开销 |
| 只用锚点，不给承托 | 零侵入 | 物品进 Play 会下落（下方无实体）→ 穿出台面 |
| 锚点 + 承托碰撞体 | 物理表现正确（能被撞掉、会滑落） | 每个锚点多一块实体碰撞体 |
| 锚点 + 冻结（`保持编辑位置`） | 零侵入 + 零物理风险，位置 100% 可控 | 物品不会被物理推动（仍是可拾取物品） |

结论：**都保留，由使用者按场景选**。因此工具里同时提供「生成承托碰撞体」与「运行时行为」，并在两者都没配时红字警告；同时单独提供内部碰撞体编辑器，供"确实需要物理表现"的场景补内腔碰撞体。工具不替使用者做这个决定，而是把三种路线的代价摆在界面上。

## 7. 已知限制与后续

**限制**

- 采样是**编辑期一次性**的，没有运行时重生成/重排；
- 落位与净空判定基于**世界 AABB**（旋转物品用 8 角点投影，偏保守：宁可略微浮起，不会陷入）；
- 锚点/目标若有**非均匀缩放**，子节点视觉尺寸与 Gizmo 会不一致（建议保持 `1,1,1` 或等比）；
- 封闭单层网格的内表面默认采不到（射线不命中背面，`Physics.queriesHitBackfaces` 默认关闭），需要用内部碰撞体编辑器或锚点绕开。

**后续可做**

- **网格三角面采样**：直接遍历 Mesh 三角形找朝上的内部面，彻底摆脱"必须有碰撞体"的前提；
- 锚点阵列/批量复制，快速摆一排货架；
- 摆放结果纳入存档（当前是场景序列化 + 编辑器生成）；
- 采样点可视化预览（干跑时在场景里画出候选点）与失败热区。
